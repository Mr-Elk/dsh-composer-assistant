# 项目优化路线（2026-11-01）

## 1. 现状盘点

**已经成立的部分**：四个功能（预测 / 续写 / 优化 / 暂存）、检查更新、125 条测试、隔离 profile
实跑、真实浏览器里的 Tab/撤销/菜单/失败保留验收、设置页与菜单对齐原生。

**还没验证的部分**：建议质量没有任何基线；IME 只有单测（你本机确认过一次组字不弹）；
DSH 0.2.1-rc.5 只做了冒烟，没有全量回归。

**还没打通的部分**：npm 未登录；发布链路曾经会把没有 `lib/` 的空包发出去。

## 2. 真正的瓶颈（按影响排序）

1. **质量没有闭环**——我们不知道一条建议“好不好”，只能靠感觉。没有固定场景、没有评分口径、
   没有可比较的前后对照。这是最该补的。
2. **发布链路脆弱**——构建产物在 git 之外、仓库在 exFAT 上装不了依赖、没有远端仓库与 CI。
3. **成本与延迟不可见**——每条建议都是一次模型调用，用户看不到花了多少、值不值。
4. **产品面仍偏大**——设置 10 行、菜单 8 项；对“输入助手”来说还能更小。

## 3. 路线

### P0 发布安全（约 1 天，可与登录并行）

- ✅ 发布门禁：`scripts/verify-publish.mjs` + `prepublishOnly`，检查 `lib/` 是否就绪、版本是否
  一致、`lib/client.js` 的模块 id 与包名是否相同、bundle 元数据是否齐全
- 版本单一来源：`package.json` 与 `src/core/version.ts` 双写，目前靠测试兜底，可改为构建时生成
- 远端与 CI：建 GitHub 仓库，Linux job 跑 typecheck / test / build / pack / package 校验，
  Windows Edge 任务保留
- 发布记录：CHANGELOG + `v0.2.0` tag

验收：`npm publish --dry-run` 内容含 `lib/`；CI 绿；tag 可追溯。

### P1 质量闭环（2–3 天，最高价值）

- ✅ 12 条固定场景：`evaluation/scenarios/core.json`，`pnpm eval:scenarios` 校验结构
- ✅ 评分表与运行说明：`evaluation/runs/README.md`，基线模板已建

- **固定场景集**：从现有 60 条合成用例（optimize/next/complete 各 20）里挑 12 条真实场景，
  人工写“期望要点”，不写死标准答案
- **评分口径**：可用 / 需小改 / 不可用三档；记录采纳前的编辑率
- **对照实验**：额外指令、温度、建议长度三组变量各跑 12 条，比较可用率
- **在线指标**：插件已有展示/采纳/编辑计数，加一个“复制本次会话统计”动作，方便取样
- 记录位置：`evaluation/runs/YYYY-MM-DD-<topic>.md`

验收：第一份基线（例如 12 条里 8 条可用），后续改动有对照而不是凭感觉。

### P2 成本与延迟（约 1 天）

- ✅ 每会话每小时的调用预算（`CallBudget`），上限改为设置项 `hourlyCallLimit`（0 = 不限制，默认 0；只作用于自动建议，手动优化不受限）

- **预算护栏**：每会话每小时最多 N 次辅助调用（内部默认 40），超出静默跳过并计数
- **缓存**：同一轮同一草稿已缓存；补一条“相同建议不重复请求”
- **流式显示**：续写逐字出现，需要评估现有 RPC 是否支持增量

验收：菜单统计里能看到调用数与跳过次数。

### P3 产品收敛（约 1 天）

- 设置从 10 行压到 7 行左右（是否把“回复后预测 / 输入续写”合成一个“建议”开关需要拍板）
- “本次使用统计”从菜单挪到设置底部
- 候选卡与提示气泡再对齐一次原生（目前已接近）

验收：设置页一屏可见；菜单 ≤ 6 项。

### 明确不做

- **候选条数**：每次多给几条，成本线性上升，收益没有证据
- **更多开关**：已经证明是负担，用户不会调
- **自绘控件**：永远追不上原生，只能借壳

## 4. 建议顺序

1. 你登录 npm，我发 0.2.0（门禁已就绪）
2. 同时我准备 12 条场景集与评分表
3. 用一周真实使用收集 20 条样本，做第一次质量评估
4. 有数据之后，再决定要不要动提示词、温度，以及是否做成本护栏

## 5. 判断标准

一个好插件不是功能多，而是：**默认好用、失败可恢复、升级不惊吓、质量可解释**。
按这个标准，当前最缺的是最后一条。
